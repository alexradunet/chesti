## Current query facts
`src/objects/views.ts` produces property paths only from validated UUIDs; values are bound. Scalar paths use `json_extract(o.properties_json, '$."UUID"')`; datetime/time-range paths compare `julianday` instants and range starts. Ordering is source-major, missing last, property, title NOCASE, UUID, with a 101-row limit/100 display cap.
Multiple-reference contains expands `json_each(...)` with NOCASE membership; canonical `object_references` already stores source/target/property edges with a target index. Writing edges have empty property ID and must not masquerade as typed property membership. Missing, empty string and empty reference array are empty; zero/false are present. Trash is excluded; commands independently recheck live scope.
Browse search is literal title/body_text substring via LIKE with ESCAPE. FTS5 trigram LIKE optimization does not support ESCAPE, short queries are a boundary, SQLite LIKE's Unicode/case behavior is not full Unicode folding. JSONB reduces parsing, not O(N) path complexity. No research paper establishes Taskdesk's best engine/query layout.

## Steps and verification
1. **Create comparable scenarios, not one flattering timing.** Reuse the small synthetic fixture. Include modest and larger scales (e.g. 1,000 and 10,000 objects), common/rare type and property selectivity, short/large writing, sparse/dense reference arrays, live/trash, and controlled history. Report fixture setup separately, engine/source version, PRAGMAs, statistics, warmups, measured repetitions and aggregate medians plus a spread (p95 or range). Default bounded run should be practical locally; document a larger optional run. Alternate comparison order where possible, collect EXPLAIN QUERY PLAN and dbstat, and verify result identity/order before comparing costs.
   - Verify small fixture tests have deterministic semantic expectations and invalid CLI limits fail safely; `bun run sqlite:bench` reports all scenario metadata without touching existing files.
2. **Property path index experiment.** Compare existing SQL against one selected, static-UUID expression index on synthetic disposable tables/data (a frequently filtered date/number path, partial live/type predicate if it matches real query syntax). Show plans before/after statistics, returned ordered IDs, read latency, index bytes, and insert/update cost. Include missing/false/zero or temporal edge semantics as relevant; do not replace instant comparison with offset string ordering. Relate the baseline predicate to actual ViewService results rather than testing two unrelated hand-written queries only. Do not add automatic per-property DDL.
   - Verify equal IDs/order for accepted equivalent scenarios and report any failure as ineligible for adoption, not a speedup. New index exists only in owned fixture DB.
3. **Reference membership experiment.** Compare current case-insensitive json_each membership with an EXISTS lookup through object_references, scoped by source, target and exact property ID. Evaluate existing indexes first; if a candidate composite index is measured, keep it synthetic and report write/storage overhead. Cover multiple properties to same target, separate writing links, uppercase stored values, missing/empty arrays, trashed sources/targets and changed edges after canonical updates. Benchmark SELECT membership only; no weakening command scope.
   - Verify both candidates agree with actual validated view evaluation IDs and order before reporting comparable timings. Small semantic tests assert the adversarial cases.
4. **Search experiment without changing its meaning.** Compare current escaped LIKE with FTS5 trigram **candidate retrieval followed by the exact original LIKE predicate** where safe. Keep stable explicit integer search identity inside the fixture, preserving public UUID identity; do not rely on VACUUM-stable hidden rowids. Queries must include one/two/three-character strings, quotes, `%`, `_`, backslash, ASCII/mixed case, Unicode, empty string and title/body matches. For shapes the candidate cannot support equivalently, use/report explicit baseline fallback or mark them ineligible rather than silently redefine search as token matching. Measure building/updating index and storage as well as reads; verify update/trash synchronization in the fixture. A conventional FTS token query can be labeled a different product, not an equivalent optimization.
   - Verify exact baseline ordered results for all claimed equivalent cases, including after mutations. Record fallback use and EXPLAIN plans honestly; LIKE ESCAPE alone is not a trigram accelerated case.
5. **Publish reproducible conclusions, not automatic adoption.** Write `docs/sqlite-benchmarks.md` with exact invocation/environment, bounded results table for read/write/storage/plan/equivalence, limitations and per-candidate adopt/defer recommendation. No promise of production speedup. JSONB and deep pagination can remain explicitly deferred because they are outside the three selected experiments; do not expand this into a storage rewrite. Include actionable follow-up only when representative evidence supports it.
   - Verify `bun run check && bun test && bun run sqlite:bench && git diff --check` succeeds. Normal tests require no network, credentials or performance thresholds. Commit scoped benchmark/report files only.
